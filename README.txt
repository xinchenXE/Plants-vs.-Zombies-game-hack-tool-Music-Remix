Funky Stars RMX (ROR Remix)
================================================================
一个 PE32 程序，双击即在 Windows 11 上播放整首曲子。
没有任何音频文件、没有声卡输入、没有第三方重放库 ——
曲子以原始 FastTracker 2 (.xm) 模块的形式内嵌在程序里，
运行期自己解析 pattern / 采样 / 包络，自己混音，自己送 waveOut。

体积
----------------------------------------------------------------
  FunkyStars.exe        67,072 字节   未压缩
  FunkyStars_upx.exe    25,088 字节   UPX --best --lzma  ← 推荐交付

  67 KB 里有 60,830 字节就是那份 .xm 本体（21,605 字节 8-bit 采样
  + 30 个 pattern 的打包数据）。也就是说 25 KB 里装的是：
  4 分 04 秒、10 声道、44.1 kHz 立体声。代码本身约 6 KB。

----------------------------------------------------------------

  FunkyStars.exe              同源的未加壳版，67,072 字节

怎么跑
----------------------------------------------------------------
  双击 FunkyStars_upx.exe，出声音；按 q 或直接关窗口退出。
  （控制台窗口会出现，这是 console 子系统，为了能收 q 键。）

实现
----------------------------------------------------------------
  * PE32 / i386，-nostdlib，入口 __start，不链 CRT。
  * 只 import：winmm（waveOut*）、kernel32（GetTickCount/Sleep/
    WriteFile/ExitProcess）、msvcrt（_kbhit/_getch）。没有 libc 初始化。
  * 采样数据是 XM 的 delta 编码，启动时一次性解成 8-bit PCM。
  * 混音：16.16 定点步进 + 线性插值，10 声道求和，输出 16-bit 立体声。
  * 音高：step = g_instK[inst] / period，每乐器一个常数把
    relative note + finetune 折进去，于是只剩一次 32 位除法
    （避免 64 位除法拖进 __udivdi3）。
  * 实现了这个模块真正用到的效果（先把 30 个 pattern 全扫了一遍，
    只出现这几种，别的完全不写进代码）：
        0  arpeggio          3  tone portamento   4  vibrato
        8  panning           A  volume slide
    以及音量列的 设定音量 / 音量滑 / 声像。
    arpeggio 全曲用了 352 次（037 = 小三和弦 0/+3/+7 共 176 次，
    047 = 大三和弦 0/+4/+7 共 176 次），整条和声层都靠它。
  * 音量包络：XM 的 10 个包络点、sustain、loop、fadeout 全部照做。
    这一点对还原度影响最大 —— 少了包络，所有音符都会变成不退的嗡鸣。
  * 每 tick 一次的音量斜坡（8.8 定点）用来消除换音爆音。

还原度
----------------------------------------------------------------
  用 libopenmpt 渲染同一份 .xm 做基准（44.1 kHz 立体声，243 秒），
  逐秒 / 逐 100 ms 窗口 / 每 10 ms 基频三重比对：
  * 整体 RMS：参考 1918 / 本程序 1928，比值 1.005，峰值 15803（无削波）
  * 逐 100 ms 电平比：中位数 1.000，有声窗口 92.6% 落在 0.8 ~ 1.25
  * 逐秒 × 9 个频段（40 Hz ~ 20 kHz）偏差中位数：
        +0.18 +0.20 +0.24 +0.16 +0.09 -0.23 -0.95 -1.48 dB
    （10~20 kHz 偏高，是本程序线性插值不带宽限、8-bit 采样的镜像噪声，
      绝对电平在 -70 dB 以下）
  * 对数频谱形态距离（灵魂比较，归一化后逐帧比对 60 Hz~8 kHz）：
        开头 3 秒 0.238（旧版 0.365）  10~13 秒 0.372  30~33 秒 0.616
  * 开头第一个和弦（G#5 + 037）逐 10 ms 追踪基频：32 个窗口里 31 个
    与参考完全一致（同一批峰位 380/420/500/620/980/1240/3600/4540 Hz）
  * 逐乐器审计（全曲 260 秒）：21 个非空乐器全部有音符、全部有发声，
    没有"触发了但一声不响"的乐器
  * 180 秒处累计时间漂移仅 16 ms

  重要教训：只看 RMS / 频段总量是查不出 arpeggio 这类问题的 ——
  arpeggio 是在同一个乐器的三个音之间轮转，总能量几乎不变，
  错误版本的电平统计一样能到 92.4%（正确版 92.6%）。
  必须用对数频谱形态距离或逐 10 ms 基频追踪才能看见。

曾经的五类"怪声"及修复
----------------------------------------------------------------
一、第一个音不对 + 整条和声层消失（最新修复，也是"缺少某个乐器"的根因）
  效果 0xy 是 arpeggio：每个 tick 在原音 / +x / +y 三个半音位置上轮转，
  6 tick 一行就是"根音-三音-五音"快速循环，听感上叠成一个和弦。
  这个模块用了 352 次（037 小三和弦、047 大三和弦），pattern 0 的
  第一个音就是 G#5 + 037。
  早期版本把这条效果误当成"声像"（k->pan = 参数），和弦全没了，
  而且顺带把声像也带偏；后来又把这段删掉，于是效果 0 完全不处理
  —— 整首曲子只剩单音旋律，第一个音自然"不对"。
  排查失误的原因：统计脚本里写了
        if ef==0: eff[(0,0)] += 1
  把参数非零的效果 0 格子也全记成 (0,0)，于是误判"效果 0 全是空参"。
  实测：修复后开头 3 秒对数频谱距离 0.365 → 0.238（改善 35%），
  0~3 秒逐 100 ms 电平比全部落在 0.97~1.04，
  第一个和弦的峰位与参考逐个吻合。

二、整段掉音 —— "听着像是缺少某个乐器"
  pattern 2 是一段 c5 独奏，大量写成 "note + 效果 3（tone portamento）
  且前一行刚 note off"。早期代码只要看到 tone portamento 就走滑音，
  但通道此时已经被 key off、音量包络已经落进衰减区（约 10/64），
  于是这些音只发出约 1/17 的电平 —— 听起来就是"这一层乐器没了"。
  正确行为：通道已经 key off（或已无音）时，note + tone porta 应当
  重新起音，包络从头开始。
  实测证据：这些行（pattern 2 的 row 6/38/54/62）在参考里 80~160 Hz
  频段能量 1,132,557，本程序只有 15,086（差 75 倍）、
  基频还停在半速（旧音的 50 Hz，正确应是 100 Hz）。
  修复后全曲逐秒电平比从"多处 0.05~0.30"回到 0.96~1.06。
  顺手修掉的第二个错误：效果 3xy 里 x 是上行速度、y 是下行速度、
  单位是 4 个周期/tick；早期版本直接把参数字节当速度（0x30=48），
  等于方向反了、速度还快了 4 倍。

三、右声道持续的嗡嗡声 + 14~22 秒拖一条长音
  XM 采样头第 14 字节的 type，bit0 才是"是否循环"的开关。乐器 6
  （index 5）的 type=0（不循环），但 loopstart=1009 / looplength=417
  这两个字段残留着非零值。早期版本只按 looplength 判循环，于是把它
  当成循环采样 —— 结果每一个用这个乐器的音都永不停止。
  而 c6/c7 正是用这个乐器的两个声道，又是硬右声像（effect 8 = E0），
  所以听到的就是：右声道每隔一拍（约 0.92 秒）叠一层新的音头，
  在一条永不衰减的嗡鸣上 → "每一秒出现一次"；c7 在 14 秒附近最后
  一个音就这样一路拖到 22 秒。
  用分离声道录音实测：修复前 c7 在 14~22 秒的 20 ms 包络恒定 61
  （最小 58），完全静止；修复后中位数回到 0，长鸣消失。
  全模块只有这 1 处 type 与 loop 字段不一致，已按 type 为准。

四、播放喂数太紧（另一个独立的断流隐患）
  早期版本 0.5 秒一块、每 0.5 秒才补一块，只领先约 1 秒；系统稍被
  抢占队列就空，驱动会反复播最后那一小段。现在改成：
    * 16 块 × 0.25 秒 = 4 秒预读，启动时一次灌满
    * 任何一块播完立刻补上，永远保持满队列
    * 写入失败不再退出循环（退出=停喂），下一轮重试
    * 关掉控制台"快速编辑"：否则鼠标点一下窗口进程会被挂起，音频断流

五、循环采样插值的右邻点
  走到循环末点要接回循环起点，之前是保持住最后一个样本，
  短循环下等于每个周期响一下 —— 细碎爆音。

排查方法（留档）
----------------------------------------------------------------
  * -DTRACE   逐行 dump 解码后的 pattern 事件流，可与 Python 解析逐字节比对
  * -DSTATE   逐行 dump 10 个声道的步进/音量
  * -DSTEMS   把 10 个声道分离导出成裸 PCM，用来定位"是哪个声道/乐器掉了"
  * -DAUDIT   每乐器的音符数 / 发声帧数 / 峰值，用来找"触发了但没声音"
  * -DRENDERTEST  整曲渲染成裸 PCM，交给 Python 与 libopenmpt 参考做
                 逐秒 RMS、逐频段能量、20 ms 包络、基频对比
  * A/B 渲染法：把可疑的那一处改成恒等（比如 k->arp = 0;）编译出一个
    对照版本，md5 比对两个渲染结果 —— 相同就说明那段代码根本没生效。
    arpeggio 的修复最终就是这样确认的。
  掉音那次是先用逐 100 ms 的 RMS 比值把问题压缩到 4 个窗口，
  再用 STEMS 确认"整段只剩 c5 在响"，最后对照 pattern 才定位到
  tone portamento 的重触发规则；arpeggio 那次则是逐 10 ms 基频追踪
  比对参考才看出来的（RMS 完全看不出来）。

关于误报
----------------------------------------------------------------
  UPX 加壳 + 自写入口 + winmm 播放，这几个特征凑在一起偶尔会被
  杀软启发式标记。如果 FunkyStars_upx.exe 被拦，用未加壳的
  FunkyStars.exe（66 KB，功能完全一样）即可。
